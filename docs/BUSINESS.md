# Бизнес-требования: что реализовано

Описывает поведение системы **как оно есть в коде**, а не как задумывалось изначально. Если фактическая реализация разошлась с исходным MVP-скоупом — это явно отмечено.

> Обновление: на момент предыдущего ревью (см. историю разработки) считалось, что ярмарки/каналы продаж не реализованы. Это больше не так — `sales_channels` и `fair-prep` реализованы и являются частью текущей функциональности ниже.

## 1. Пользователи и авторизация

- Регистрация по email + паролю (`POST /auth/register`), пароль хранится как bcrypt-хэш.
- Вход выдаёт пару токенов: `access_token` (30 минут) и `refresh_token` (30 дней).
- `POST /auth/refresh` обновляет `access_token` по `refresh_token`; сам `refresh_token` не ротируется и не хранится в БД — это простой stateless JWT, отозвать конкретный refresh-токен на сервере нельзя.
- Каждый защищённый эндпоинт требует `Authorization: Bearer <access_token>` и подтягивает пользователя по `sub` из токена.
- Данные каждого пользователя изолированы: все выборки фильтруются по `user_id`, принадлежность проверяется перед любой операцией над чужим ресурсом (иначе 404).

## 2. Изделия (products)

- Изделие — товар, который производит и продаёт мастер: название, категория, цена продажи, остаток на складе, необязательное фото.
- Категория — свободная строка. Список категорий-подсказок хранится в настройках пользователя (`user_settings.categories`), но на уровне БД ничего не мешает создать изделие с любой другой категорией.
- **Себестоимость (`cost_price`) считается на лету**, а не хранится: сумма `product_materials.quantity * materials.price_per_unit` по составу изделия, по **текущим** ценам материалов. Если цена материала меняется, себестоимость уже проданных/существующих изделий "задним числом" пересчитывается при следующем запросе — это не исторический снимок себестоимости на момент производства.
- Список изделий поддерживает пагинацию (`page`, `per_page`), фильтры `category` и `in_stock`, и отдаёт `total_stock_value` в `meta` — сумму `stock_qty * sale_price` по всем изделиям, попадающим под фильтр (не только по текущей странице).

### Фото изделия
- `POST /products/{id}/photo` принимает файл, конвертирует в RGB, уменьшает до 800×800 (Pillow `thumbnail`, сохраняя пропорции), пережимает в JPEG (quality 80) и хранит как **base64-строку прямо в колонке `products.photo`** — не файл на диске и не объектное хранилище.
- `DELETE /products/{id}/photo` просто обнуляет колонку.

### Состав изделия (product_materials)
- К изделию можно привязать материалы с указанием расхода на одну единицу (`POST /products/{id}/materials`).
- Один и тот же материал нельзя добавить в состав дважды — только удалить и добавить заново с новым количеством (ограничение `UNIQUE(product_id, material_id)` на уровне БД и явная проверка в роутере, возвращающая 400).

### Производство (списание материалов)
- Материалы списываются со склада **только** при увеличении `stock_qty` изделия через `PUT /products/{id}` — то есть при регистрации факта "сделал ещё N штук". Разница `new_stock - old_stock` умножается на расход каждого материала в составе и вычитается из `materials.stock_qty`.
- **Важная асимметрия**: при **создании** изделия с ненулевым начальным `stock_qty` (`POST /products` с `stock_qty > 0`) материалы **не списываются** — списание срабатывает только на `PUT`. На практике это значит: если завести изделие сразу с остатком (например, при первоначальном заполнении каталога), запас материалов не уменьшится, а если потом увеличить остаток тем же способом — уменьшится.
- Уменьшение `stock_qty` через `PUT` **не** возвращает материалы на склад — списание материалов работает только в одну сторону (при увеличении).
- Продажа (см. ниже) списывает только `products.stock_qty`, но не трогает остатки материалов повторно — списание материалов и списание готовых изделий это две независимые операции над разными сущностями.

## 3. Материалы (materials) и склад

- Материал: название, единица измерения (свободная строка, подсказки — `user_settings.material_units`), цена за единицу, остаток на складе.
- **Себестоимость материала — средневзвешенная**, а не FIFO/LIFO: при пополнении (`POST /materials/{id}/restock`) с указанием новой цены рассчитывается
  ```
  new_price = (old_stock * old_price + restock_qty * restock_price) / (old_stock + restock_qty)
  ```
  Если новая цена не указана — используется текущая цена материала, взвешивание не требуется.
- Если материал создаётся сразу с `stock_qty > 0`, это тоже считается закупкой — создаётся запись в `material_purchases` на дату создания.

### Учёт закупок материалов
- Каждое пополнение (при создании материала с остатком или через `/restock`) создаёт строку в `material_purchases`: количество, цена за единицу на тот момент, и `total_cost` (посчитан и сохранён сразу, не на лету).
- Эта таблица — источник данных для расходов на материалы в дашборде (`material_expenses`), независимый от таблицы `expenses` (ручных расходов).
- Удаление материала не удаляет историю закупок автоматически из бизнес-логики — каскад определён на уровне БД (`ON DELETE CASCADE` на `material_purchases.material_id`), так что при удалении материала пропадёт и его история закупок, включая уже отражённые в прошлых периодах суммы дашборда.

## 4. Каналы продаж (sales_channels) и подготовка к ярмарке

- Заменяют более раннюю сущность "покупатель" (`buyers`, теперь не используется в API — см. [DOMAIN.md](DOMAIN.md#buyers)).
- Канал — это не обязательно ярмарка: тип `лс` (личные продажи), `ярмарка`, `другое`. Тип — свободная строка, не enum в БД, ничего не мешает завести произвольное значение через API.
- Продажа может быть не привязана ни к какому каналу (`channel_id` nullable).

### Подготовка к ярмарке (fair-prep)
- Для каналов с типом `ярмарка` доступен отдельный планировщик: к каналу привязывается список изделий с "запланированным количеством" (`planned_qty`).
- Сервер на каждый запрос вычисляет `need_to_make = max(0, planned_qty - product.stock_qty)` — сколько ещё нужно доделать, чтобы набрать запланированное количество на ярмарку. Значение не хранится, всегда актуально на момент запроса.
- Поддерживает фильтр по категории и сортировку (по имени, категории, цене), список позиций — уникальные пары "канал + изделие" (`UNIQUE(channel_id, product_id)`), повторно добавить то же изделие нельзя.
- Это только **планирование** — сам список не списывает и не резервирует остатки, это независимый от продаж и производства слой поверх тех же данных.

## 5. Продажи (sales)

- Продажа = дата + необязательный канал + необязательные заметки + список позиций.
- Каждая позиция (`sale_item`) хранит `product_id` (nullable — товар может быть удалён позже, позиция останется), `quantity`, и `price` — **цена копируется в позицию на момент продажи** и дальше живёт независимо от текущей `sale_price` товара. Изменение цены изделия задним числом не меняет уже оформленные продажи.
- При создании продажи `stock_qty` соответствующего изделия автоматически уменьшается на `quantity` каждой позиции. Уйти в минус ничего не мешает — проверка на достаточность остатка не выполняется.
- При удалении продажи остаток изделий по всем её позициям **восстанавливается** (`stock_qty += quantity`) — но только если товар с таким `product_id` всё ещё существует.
- `total_amount` не хранится — считается на лету как сумма `quantity * price` по позициям, всегда в сервисе `calc_sale_total_amount`.
- Обновление продажи (`PUT`) меняет только "шапку" (дата, канал, заметки) — изменить состав позиций после создания через API нельзя, только удалить продажу целиком и создать заново.

## 6. Расходы (expenses)

- Ручной учёт расходов: категория (свободная строка, подсказки — `user_settings.expense_categories`), сумма, дата, описание.
- Не связаны с материалами — расходы на закупку материалов учитываются отдельно через `material_purchases` (см. раздел 3) и попадают в дашборд как отдельная статья.

## 7. Настройки пользователя (user_settings)

- Создаются лениво при первом `GET /settings` со значениями по умолчанию (в т.ч. категории на русском под нишу "handmade игрушки").
- Хранят: валюту, список категорий изделий, список категорий расходов, список единиц измерения материалов, порог низкого остатка (`low_stock_threshold`).
- Эти списки — это ровно и только подсказки для UI (выпадающие списки), они не валидируются на бэкенде: изделие/расход/материал с категорией/единицей, отсутствующей в списке настроек, создать можно, ошибки не будет.

## 8. Дашборд

- **Сводка** (`/dashboard/summary`, с опциональным диапазоном дат): выручка (сумма по позициям продаж), расходы = ручные расходы (`expenses`) + расходы на материалы (`material_purchases.total_cost`), прибыль = выручка − расходы.
  - Себестоимость проданных изделий (COGS) в эту прибыль отдельно не вычитается — расход на материалы уже учтён через сумму их закупок, повторный вычет себестоимости изделий задвоил бы расход. Прибыль здесь — это "выручка минус все траты за период", а не "выручка минус себестоимость проданного".
- **Топ товаров** (`/dashboard/top-products`) — по выручке за период, с лимитом.
- **Низкий остаток** (`/dashboard/low-stock`) — изделия с `stock_qty <= threshold` (по умолчанию 5, но не привязан автоматически к `user_settings.low_stock_threshold` — фронтенд должен сам передать сохранённое значение параметром).

## 9. Экспорт / импорт (в разработке, не в основной ветке на момент написания)

- Полный экспорт всех таблиц пользователя одним ZIP-архивом с CSV-файлами (`GET /export/csv`), включая устаревшую таблицу `buyers`.
- Импорт того же формата (`POST /import/csv`) — построчная вставка с `ON CONFLICT DO NOTHING` по `id`, то есть повторный импорт не перезатирает изменённые записи, только досоздаёт отсутствующие. Исключение — `user_settings`: там `ON CONFLICT DO UPDATE`, настройки при импорте всегда перезаписываются.
- Задумано как способ переноса данных между окружениями и как резервное копирование "на всякий случай" — не транзакционный slot-in бэкап/рестор с учётом версий схемы.

## Явно НЕ реализовано

- Отмена/изменение состава уже созданной продажи (только удаление целиком).
- Проверка отрицательного остатка при продаже или при увеличении `stock_qty` изделия без достаточного запаса материалов — операция просто уходит в минус.
- Резервирование остатков под план ярмарки (`fair-prep` — это калькулятор "сколько не хватает", не резерв).
- Ролевая модель/шаринг данных между пользователями — один пользователь видит только свои данные, совместных аккаунтов или ролей нет.
- Отзыв конкретного refresh-токена (logout только на клиенте, токен остаётся валиден до истечения).
